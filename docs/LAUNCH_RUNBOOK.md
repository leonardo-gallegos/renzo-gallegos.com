## Deployment procedure — owner

1. Record reviewed merge SHA, successful Actions run URL, artifact name/download date and public configuration state in RELEASE_V1. Download that run's `hostinger-static-out`, extract outside the web root and inspect its contents. A local `out` is useful for rehearsal but does not prove hosted CI passed.
2. Confirm the exact account/domain/document root in hPanel. Back up **the full existing public_html including hidden .htaccess** to a dated directory outside every served root, and download a second copy. Record its actual absolute location below. Confirm it can be restored. Backups must not be accessible by URL.
3. Confirm valid apex/www certificates and canonical HTTPS settings. Stage a complete artifact outside the web root if the hosting plan permits a tested document-root swap. Otherwise schedule a quiet upload window: in-place uploads can briefly mix builds.
4. Upload the **contents** of the artifact into `public_html`, with no enclosing `out/`. Preserve `_next`, `es`, `en`, `cv`, `images`, localized feeds, sitemap, robots, manifest, index and 404. Keep approved hosting configuration; it is not generated by Next. Never upload repository/source/DOCX/.env/Git/QA files.

6. Apply provider-compatible HTTPS/canonical/error/MIME/cache/header settings from DEPLOY_HOSTINGER. Serve directory `index.html` and exported `404.html` with **status 404**; no SPA catch-all or Home-with-200 fallback.
7. Purge provider/CDN caches as needed. Run the HTTP smoke script, then browser/SEO/privacy/social/performance checks below. Record evidence and incident decisions before tagging.

### HTTP smoke method

Run on the operator's Node 22 machine after deployment, not on Hostinger:

```sh
npm run smoke:live
```

For machine-readable evidence outside the repository/artifact, run `node scripts/smoke-test-live.mjs > /operator/evidence/live-smoke.json` with an actual chosen evidence path. Exit 0 means the script's checks passed; exit 1 identifies failed probes. Each request has a 15-second timeout, requests are sequential, and certificates retain normal verification. Never disable TLS validation.

Local rehearsal only: `npm run smoke:live -- --base-url http://127.0.0.1:4176` against a running static server serving out with proper MIME/404 responses. This mode skips external host redirects and is explicitly labeled **not live evidence**. The script uses native fetch and no browser package. It checks launch URLs/status/body signatures/basic production metadata, discovers referenced first-party CSS/JS, probes their MIME/source-map absence and selected private paths. It records headers without pretending to approve their policy. It does not validate every XML structure, link, secret, unknown source path, PDF language, browser interaction, platform integration or field performance; complete the manual checks.

### Redirects, MIME, caching and headers

- Test HTTP apex, HTTP www and HTTPS www with `/es/blog/estructurar-pi-af-operacion-minera/?launch-check=1`. Require permanent 301/308 chains to exact HTTPS apex with path/query retained, valid www certificate and no loop. The production script exercises all three. Test ordinary slash/non-slash navigation too. Hosting handles redirects; no Next runtime redirect.
- Use `curl.exe -I URL` in PowerShell (or `curl -I` elsewhere) and browser Network to supplement GET results. HTML `text/html`; CSS `text/css`; JS `text/javascript` or valid JavaScript equivalent; sitemap/XML `application/xml` or `text/xml`; feeds may use `application/rss+xml`; PNG `image/png`; PDFs `application/pdf`; manifest `application/manifest+json` or suitable JSON equivalent. Record actual discrepancies before correcting Hostinger configuration.
- Hashed `/_next/static/*`: recommended `Cache-Control: public, max-age=31536000, immutable`. Mutable HTML, sitemap, robots, feeds, manifest, stable-name social image and PDFs need revalidation or a short TTL (for example max-age=300), not immutable year-long caching. Check actual headers and fresh content after deploy/rollback; do not assume the hosting example is active.
- Record HTTPS/content-type/cache-control, Referrer-Policy, X-Content-Type-Options (nosniff), X-Frame-Options or CSP frame-ancestors, Permissions-Policy and CSP vs report-only state on HTML/assets/errors. See the compatibility draft in DEPLOY_HOSTINGER. Start report-only, verify theme/bootstrap/CSS/fonts and any GA/Giscus before enforcement. Do not deploy a breaking CSP merely to complete a checkbox.

## Incidents and rollback

| Severity | Examples | Action |
| --- | --- | --- |
| Critical | Site unavailable, broken CSS/JS, HTTPS or locale failure, wrong CV, private/unintended file exposure | Roll back immediately; remove confirmed exposure through the verified root procedure and escalate to owner |
| Major | Sitemap/robots, one article, redirects, social card, GA/Giscus malfunction | Fix forward or roll back according to impact and restoration time |
| Minor | Typo, small visual defect, noncritical metadata inconsistency | Reviewed fix forward |

Rollback restores a **complete previous artifact**, not individual old HTML files:

1. Record incident/time/failed SHA; stop concurrent uploads. Verify correct root and full backup outside web root. Preserve a failed-release evidence copy outside served directories if needed; do not expose private material through backups.
2. Prefer the provider's tested whole-directory switch to a verified coherent prior release. If unavailable, use a quiet maintenance window, restore prior hashed assets first, then matching prior documents/CV/images/SEO/feeds and prior approved hosting configuration. In-place restoration is not atomic; remove files absent from the backup after root/inventory verification so builds do not remain mixed.
3. Purge HTML/provider/CDN caches; preserve matching assets until prior documents are restored. Verify the resulting inventory against backup and record restored SHA/config/time.
4. Rerun HTTP smoke, redirects, real 404, both locales and CVs, asset loads, privacy paths, browser navigation/theme and SEO files. Confirm the original critical failure is gone. If an older release predates required blog/CV URLs, document that restoration explicitly rather than interpreting missing newer URLs as successful V1 validation.
5. Fix on a reviewed branch, rerun CI and deploy a new complete artifact. Never leave a partially repaired mix. Update release evidence and incident log.

## Tag and follow-up

Only after merged SHA, hosted CI, deployment and live validation are confirmed, use a clean checkout and verify main HEAD is the **exact deployed SHA**, the intended tag does not already exist, and no newer unvalidated main commit is being tagged. Owner-only commands, not executed by this task:

```sh
git checkout main
git pull origin main
git tag -a v1.0.0 -m "Initial public release"
git push origin v1.0.0
```

If main moved, stop and resolve the revision choice rather than tagging a different artifact. Record final tag/SHA and platform evidence in RELEASE_V1. Review indexing weekly initially and SEO_BASELINE at 30/60/90 days. CONTENT_ROADMAP plans substantive future writing; it publishes no routes. Task 07 is outside this runbook's implementation scope.
